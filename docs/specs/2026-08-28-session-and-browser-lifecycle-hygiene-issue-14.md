# session and browser lifecycle hygiene (issue 14)

> webglass never leaves a session record or headless browser nobody can see or reap: ephemeral navigations are labelled honestly, doctor warns on session-store growth, and session clean --older-than sweeps stale records and orphaned browsers
> instruction: Verify end to end on a real store: seed expired records for two different callers, run an ordinary session-creating invocation as one of them, assert only that caller's records were reaped and a read verb reaps nothing; separately assert a navigating verb with no --session-id renders ephemeral: true.

## Audience

- Agent callers driving webglass one-shot from another process — colleague's web-scout being the reporting one (agentculture/colleague#436) — plus the human operating the host they share, who is the one who has to notice and clear a session store nobody is sweeping.
  - instruction: Write every user-facing string in this slice for both readers: an agent parsing --json and a human reading 'doctor' text output.

## Before → After

- Before: Nothing sweeps the store: `_op_session_clean` is the only caller of store.clean in the package, so a host accumulated 134 records — 115 closed-but-within-retention and 19 marked 'active' though they expired ~20 days ago with dead pids. Every CLI navigation reports ephemeral: false regardless, 'session clean' takes no flags, and 'doctor' has five browser checks that never look at the session store.
  - instruction: Re-run the before-state measurement on the reporting host before and after the change, and put both numbers in the PR body as evidence.
- After: A webglass invocation is honest about the session it ran in and leaves nothing that grows without bound: a throwaway navigation reports ephemeral: true, a record whose browser is gone says so instead of reading 'active', ordinary invocations sweep the store opportunistically, 'session clean' takes filter flags, and 'doctor' warns when the store has grown past a healthy size.
  - instruction: Treat the after-state as the acceptance checklist: five separately observable behaviours, one test each (h19, h22).

## Why it matters

- The observability gap cost a real investigation: issue #14 read 126 session records plus 187 chromium processes as one leak and filed all three asks against webglass, when the ephemeral close path was working correctly (115/115 records `browser_reaped`=true) and the 187 processes were the reporter's desktop snap Chromium. A store that never sweeps and a label that always says 'false' made a healthy subsystem indistinguishable from a leaking one.
  - instruction: Answer issue #14's three asks individually in the closing comment, naming which rested on the wrong premise (the 187 chromium processes) so the record is corrected where it was filed.

The operation, not the service, must carry the invocation-scoped-vs-caller-owned fact.
  - instruction: Carry the invocation-scoped fact on the WebOperation (or WebContext) set by `ephemeral_session`, and have `_session_for_navigation` (service.py:1194) read it instead of inferring from `session_id` is None.
  - honesty: The ephemeral fact travels on the WebOperation (or context), not inferred in `_session_for_navigation` — so a library caller who creates a session explicitly and a CLI throwaway are distinguishable, and library/CLI parity (spec honesty h2) still holds because both report the same field from the same source.
- `webglass doctor` gains a session-store health check alongside the five browser checks in webglass/cli/`_browser_doctor.py` (`browser_checks`(), lines 358-366): live/stale session counts and record-directory size, warning above a threshold. Doctor's `{healthy, checks:[{id,passed,severity,message,remediation}]}` shape and the `passed=True for every severity except error` convention are the contract to extend, not change.
  - instruction: Add a session-store check to `browser_checks`() (`_browser_doctor.py`:358-366) returning severity=warning with passed=True above the threshold, following `check_state_dir_writable`'s shape.
  - honesty: The session-store check is read-only and cheap: it counts records and probes recorded pids without launching a browser, holding a lock, or mutating a record — matching the existing browser checks, none of which ever launches anything.
- `session clean` gains an `--older-than` sweep. Today `FileSessionStore.clean` (`session_store.py`:533-578) only expires actives past `expires_at`, drops dead leases, and purges non-active records older than `DEFAULT_RECORD_RETENTION_SECONDS` (7 days, line 167).   - instruction: Keep store.clean as the single reaping implementation; add the opportunistic caller (c14) and the filter flags (c13) around it rather than a second cleanup path.
  - honesty: store.clean grows an explicit filter argument rather than the CLI post-filtering its results: the store is the only thing that holds the per-record lock, so a caller that reads-then-decides would race a concurrent invocation.

All 19 stale records on the host are `status=active, browser_reaped=false, browser_was_running=null` with dead pids — `session list`/`show` render `to_public_dict()` (`session_store.py`:403-416) verbatim and never probe liveness, so a crashed caller's session reads as live indefinitely. The store already has `_is_running` (line 264) for exactly this question.
  - instruction: Probe record.pid with the existing `_is_running` (`session_store.py`:264) at render time in `to_public_dict`()'s consumers; report it as an observed liveness field, never by mutating status on a read path.
  - honesty: Liveness is reported as an observed fact at render time, never written back as a silent status mutation on a read path — 'session list' must not mutate records, and a pid that is alive but reused by another user's process must not be claimed as ours.

- 'session clean' gains filter flags — --older-than at minimum, plus further selectors such as by site. Today the clean parser (cli/`_commands`/session.py:145-148) takes no flags at all and store.clean(now) takes only a clock reading, so both the CLI surface and the store signature grow.
  - instruction: Extend the clean parser (cli/`_commands`/session.py:145-148, which takes no flags today) and store.clean's signature together — filters are evaluated inside the store under its per-record lock, never by post-filtering results in the CLI. Cover --older-than, --status, and --site; a malformed duration is a structured `invalid_argument`.

It must be cheap and bounded (the store already locks per record and 272 files were on the reporting host), must not turn a successful observation into a failure, and must not reap another caller's live sessions.

- The opportunistic sweep must not kill a live browser mid-operation. `expires_at` is written once at create (`session_store.py`:485-486) and never extended — `acquire_lease` refreshes `last_used_at` and the lease but not `expires_at` — while the ephemeral TTL is 300s (`_factory.py`:216). Manual-only cleanup makes this rare today; c14/c24 makes it routine. The sweep must treat a held lease, or a refreshed expiry, as proof of life.

  - instruction: Add a diagnostics/effects field carrying what the sweep reaped, and assert it in the JSON envelope test from h25.

  - instruction: Build the doctor check on a corruption-tolerant read rather than list(), and have it report the corrupt record as a finding. Add the planted-corrupt-record test from h26.
  - honesty: A test plants a corrupt record and asserts 'doctor --json' still returns its full check list, naming the corrupt record rather than failing to run.

  - instruction: Call `bump_generation` (`session_store.py`:631) on reuse and add the stale-reference test from h27.

Verified on the reporting host: all 115 `ephemeral-*` records are `closed` with `browser_reaped=true, browser_was_running=true`, and zero `ephemeral-*` records are stuck `active`. Issue #14 ask 1's cleanup half is already implemented; only the label is wrong.
  - instruction: Do not rewrite `ephemeral_session`'s finally-close or FileSessionStore.close. Add the regression test from h14 so the working behaviour is pinned before anything else in this slice moves.
- Detached launch stays detached. `launch_detached` (webglass/adapters/playwright.py:416-480) uses `start_new_session=True` deliberately — it is what makes cross-invocation sessions (spec claim c29) work — so a group-killed CLI cannot take its browser with it. The fix is reaping by record, not un-detaching the launch.
  - instruction: Leave `launch_detached` alone and add the test from h15 pinning `start_new_session`=True.
- M3 surfaces stay untouched. Evidence, exploration, and Web-memory (webglass/evidence.py, exploration.py, memory.py) are unbuilt per issue #8; this work touches only the session-lifecycle plane — service.py session ops, adapters/`session_store.py`, cli/`_factory.py`, cli/`_commands`/session.py, cli/`_browser_doctor.py`, cli/`_commands`/doctor.py — plus their explain-catalog entries.
  - instruction: Extend tests/`test_import_boundaries.py` with the session-plane assertion from h16.
- Recording visited hosts on a persistent 0600 session record is new retained browsing data and must be treated as a privacy decision, not a free field — issue #1 section 8's 'never persist by default' list and the redacting repr() that already keeps `endpoint_ref` out of every render are the precedent. Scope, retention, and redaction of any host field are decided explicitly, not inherited from --site's convenience.
  - instruction: Keep the host field out of FileSessionRecord's redacting repr (`session_store.py`:378-402) the way `endpoint_ref` already is; add the test from h17.
- The retained mapping is proto-Web-memory and inherits its rules, not a new exception to them. Issue #1 section 2 makes Web-memory a searchable index that answers 'have we seen this?', never silently injects old content into a new answer, and is never a credential store. A 3-day host mapping that saves tokens must obey all three — and stays a mapping, not a content cache, since the durable evidence/memory stores themselves are M3 (issue #8).
  - instruction: Bound the mapping entry's fields to host-level facts and assert that bound in a test (h23), so it cannot grow into the content cache M3 owns.
- The sweep is an unrequested destructive local-state effect and must be classified as one. Issue #1 section 3 requires a local-state effect to run under an authorized state scope and retention policy; killing a process and rmtree-ing a profile directory is irreversible, and here it happens as a side effect of a caller asking for something else. It stays inside WebGlass-owned state — never another caller's live session, never a process WebGlass did not launch (c6).
  - instruction: Classify the sweep as a local-state effect in effects.py terms and keep it inside WebGlass-owned state; never a process WebGlass did not launch (c6), never another caller's live session.

## Assumptions

- Filtering 'session clean' by site requires a record field that does not exist. A live record carries `backend_id`/caller/owner/task/pid/`user_data_dir`/status/`expires_at` and no URL or host whatsoever, so --site implies adding a visited-host field, bumping `RECORD_SCHEMA_VERSION` from 1 (`session_store.py`:144), and writing the migration note docs/schema-versioning.md requires for every bump.
  - instruction: Confirmed as an assumption: --site is built on the new host field, accepting the schema and privacy cost recorded in c16/c25.
- c24's 'only the invoking caller's records' and c23's 'the invoking caller's last 3 sessions' both assume caller identity distinguishes concurrent invocations. It does not: `_DEFAULT_CALLER` = 'cli' (`_factory.py`:208) is hardcoded for every CLI invocation, and all 134 records measured on the reporting host carry caller='cli'. Filtering by caller therefore selects every CLI record on the host — the isolation promised in q2 and q5 does not exist at the identity layer.
  - instruction: Do not build c23 reuse or c24 caller-scoped sweeping until v4 resolves — caller-scoping is a no-op while `_DEFAULT_CALLER` is the literal 'cli'.
- The owner token identifies the long-lived CLIENT, not the one-shot OS process — this is what makes the model work. Under the Playwright-MCP analogy the server instance outlives individual calls, so a client such as colleague keeps one owner token across its many one-shot 'webglass' invocations. A token minted per OS process would make the sweep useless (each invocation owns exactly one session and would reap nothing), which was the objection that made v4 blocking; a per-client token is both safe and effective.

## Decisions

- Session ownership follows the Playwright-MCP model: the client/process that opened a session owns it, and ownership scopes sweeping and reuse. This replaces caller-string scoping, which c29 showed is a no-op because `_DEFAULT_CALLER` is the literal 'cli' for every invocation.
- REVISES q2/c24. Identity and the sweep are decoupled: the sweep is owner-agnostic and gated on LIVENESS (lease held or expiry refreshed, per c28), not on ownership — an expired record means its owner is finished or crashed, and reaping it is safe and is what 'session clean' already does store-wide with a warning (service.py:2191-2198). A unique owner id is load-bearing only for continuation/reuse eligibility (c23). This dissolves c36's objection: sweep effectiveness no longer depends on a long-lived token, so a per-invocation unique id suffices.
  - instruction: Gate clean() on liveness only; keep the cross-owner warning from `_op_session_clean`. Scope the owner token to reuse matching alone.
- c36 is superseded by c38: the owner token no longer needs to identify a long-lived client. A unique id assigned per invocation is sufficient, because it now serves only continuation/reuse eligibility and never sweep scoping.
  - instruction: Mint a unique owner id per invocation; a continuation call passes the prior id explicitly to claim eligibility.

## Hard questions

- Which invocations sweep? Sweeping on every invocation including 'session list' means a read verb mutates the store the caller is trying to observe; sweeping only on session-creating invocations means a host that only ever reads never gets cleaned. (resolved: Retention drops from 7 days to 3 days, and the 3-day window exists for a reason beyond forensics: records are kept so repeated visits can be found and mapped, enabling session reuse. This supersedes the earlier q1 answer (c12) that kept the 7-day `DEFAULT_RECORD_RETENTION_SECONDS`.)
- Whose records does an opportunistic sweep touch? store.clean() is store-wide and `_op_session_clean` already warns that it reaped other callers' expired sessions — an automatic sweep doing that silently, with no output surface to warn on, reaps another caller's records with nobody told. (resolved: The opportunistic sweep runs on new cases only (a session-creating invocation, never a read verb) and touches only the invoking caller's own records; store-wide reaping stays explicit via 'session clean'. A new case is matched against the recent (last 3) sessions for the repetition/reuse mapping.)
- Which host does --site match when a session navigated to several? A session record is per-browser-context, not per-page, so 'the site' is a set — and matching on a set turns 'clean --site x' into 'reap any session that ever touched x', which is a different and broader promise than it sounds. (resolved: --site is confirmed in scope as asked, with the new persisted visited-host record field and the privacy decision it implies. The same field serves the repetition mapping from q1, so it is no longer a cost carried by --site alone.)
- Does reuse mean reusing a still-ACTIVE session, or resurrecting a CLOSED one? `_reap_browser` (`session_store.py`:791-808) rmtree's both record.`user_data_dir` and the profile path on every close, so a closed record is a tombstone with no browser and no cookies left to reuse. Reusing an active session needs no retention change at all; resurrecting a closed one requires keeping the profile directory on disk for the 3-day window — which is retaining cookies, storage, and login state, not just a record. (resolved: Reuse means reusing a still-ACTIVE, unexpired session — never resurrecting a closed one. `_reap_browser` keeps deleting the profile directory on close, so no cookies or storage are retained. The 3-day retention window exists for the mapping, not for the browser state.)
- How does reuse stay inside 'isolated per caller/task'? Issue #1 section 2 makes a browser session isolated per caller/task, and CLAUDE.md's invariant list says child agents never accidentally share cookies or mutable tabs. Matching a new case to a prior session by host and reusing it shares exactly that state across two tasks — so what makes two cases eligible to share, beyond same caller and same site? (resolved: Sessions are never shared across tasks. Reuse is scoped to the immediate flow — a subsequent webglass call that is a continuation of the current one — so 'isolated per caller/task' and 'children never share cookies or mutable tabs' both hold unchanged. What is retained across the 3-day window is the mapping, not the session.)
- What distinguishes two concurrent webglass invocations, given caller is 'cli' for all of them? Without an answer the sweep reaps a sibling process's sessions (q2's promise fails) and reuse can hand a session belonging to a different task (q5's promise fails). Candidates: derive caller from the OS process/session, require callers to pass an explicit --caller/--task, or scope both sweep and reuse to ids minted by this process. (resolved: Parked for now rather than answered — see the parked blocking unknown recorded alongside c29. The identity model is not settled in this pass.)

## Resolved vagueness

- [unknown_nonblocking] Whether the opportunistic sweep should be bounded by count (reap at most N records per invocation) or by time (spend at most Nms), and what that bound is. Both keep 'page open' fast; a count bound is deterministic and testable, a time bound degrades gracefully on a slow filesystem. — resolved: The sweep is bounded by TIME: it spends at most a fixed budget per invocation and stops, degrading gracefully on a slow filesystem rather than blocking a fast one behind a fixed record count. Ties to c37's under-50ms target.
- [follow_up] Whether --site is worth its cost at all in this slice. It is the only ask requiring a new persisted record field (c15) and a privacy decision (c16); --older-than and --status filters need neither and cover the reported symptom. Deferring --site to a follow-up would let this ship without touching what a session record retains. — resolved: --site stays in this slice. The user confirmed it, and the visited-host field it needs is no longer a cost carried by --site alone: the same field is what repetition-mapping (c23) matches on.
- [unknown_nonblocking] Whether non-Linux hosts are in scope for the sweep. `terminate_pid` uses os.kill/SIGTERM/SIGKILL and `_locked` uses fcntl.flock (`session_store.py`:290-327, 696-708) — both POSIX-only, and the store is already Linux-shaped before this change. The sweep does not make it worse, but automating process termination raises the cost of the assumption if it is ever wrong. — resolved: Confirmed POSIX-only. `terminate_pid`'s os.kill/SIGTERM/SIGKILL and `_locked`'s fcntl.flock are accepted platform constraints; the store is already Linux-shaped and the sweep does not widen that.
- [unknown_blocking] How two concurrent webglass invocations are distinguished, given `_DEFAULT_CALLER` = 'cli' is hardcoded for all of them (c29). Blocking because c24's caller-scoped sweep and c23's caller-scoped reuse are both unsafe under the current identity model: the sweep would reap a sibling process's sessions and reuse could hand over another task's session. Candidates: derive caller from the OS process, require an explicit --caller/--task, or scope both to ids minted by this process. — resolved: Identity follows the Playwright-MCP model: a session belongs to the client/process that opened it, and that owner — not the literal 'cli' caller string — is what scopes both the sweep (c24) and reuse (c23). An invocation may only reap or reuse sessions its own owner opened; another owner's sessions are invisible to it, exactly as one MCP server instance cannot touch another's browser.
